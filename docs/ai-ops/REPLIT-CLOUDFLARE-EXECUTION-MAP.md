# Replit / Cloudflare execution map — AI operations

Operator tasks that need direct Cloudflare access, in the same shape as
[REPLIT-CLOUDFLARE-PROMPT-gaps.md](../../REPLIT-CLOUDFLARE-PROMPT-gaps.md) at
the repo root — this file extends that convention for the AI layer, it does not
replace it. Claude Code inspects the repo and writes these; Replit, which holds
direct Cloudflare API/dashboard access, runs them.

**A note on how to read this file.** Each task states what was verified from the
checkout and what could not be — a control-plane fact (does a gateway exist? is
a secret set?) is never assumed from code that merely reads it. Secrets are
named, never printed. Every task ends with a verification that does not trust
the command's own exit code.

---

## Task A1 — Create an AI Gateway and set `AI_GATEWAY_ID`

**Why this matters:** the code is gateway-aware (`worker/src/analyzers/llm.js:65`,
`worker/src/fix/providers.js:143`) but no gateway is configured, so `resolveModel`
falls to Kimi **K2.6** and never reaches **K3** — which is reachable only through
a gateway (`llm.js:129`). A gateway is also the only source of Cloudflare-native
AI analytics, caching, and spend controls. This one change unlocks both the
better model and the metering plan's Cloudflare half.

**What was verified.** `AI_GATEWAY_ID` appears in code as an `env` read only; it
is **not** in `wrangler.toml` vars and **not** in the required-secrets block
(`wrangler.toml:487`). So it is unset in production. **Not verifiable from the
checkout:** whether a gateway already exists on the account under another name.
Check that first — do not create a duplicate.

```bash
cd worker
# 1. List existing gateways — reuse one if it already exists.
./node_modules/.bin/wrangler ai-gateway list
# 2. Create one if none is suitable (name it for the platform).
./node_modules/.bin/wrangler ai-gateway create algosize-ai
# 3. Bind its id as a secret (the value is the gateway name/id from step 2).
./node_modules/.bin/wrangler secret put AI_GATEWAY_ID --config wrangler.toml --env production
```

**Then verify from outside the exit code.** Trigger one AI-backed action —
generate a fix on any finding — and confirm in the Cloudflare dashboard's AI
Gateway view that a request appears. If requests appear, the gateway is live and
K3 is now the default (`resolveModel` returns `KIMI_K3` when a gateway is set).
If none appear, the binding did not take — re-check the secret name is exactly
`AI_GATEWAY_ID`.

**Rollback.** Unset the secret: `wrangler secret delete AI_GATEWAY_ID`. The code
falls straight back to the keyless K2.6 binding with no other change.

## Task A2 — (Optional) set `ANTHROPIC_API_KEY` for the `claude` fix provider

**Why this matters:** the fix pipeline's provider order is
`["kimi", "claude", "openai"]` (`providers.js:253`), but "configured" is judged
from env shape (`providers.js:264`) and only `kimi` has credentials in
production. So every fix is generated by Kimi today. Setting the Anthropic key
makes `claude` selectable and enables `compareAlternativeFixes`
(`providers.js:293`) to run a real second opinion.

**What was verified.** `ANTHROPIC_API_KEY` is read in `providers.js` and the
Anthropic path (`chatAnthropic`, `providers.js:154`) is complete, but the key is
absent from `wrangler.toml`. **Not a blocker** — kimi works without it. This is
a capability add, not a fix.

```bash
cd worker
./node_modules/.bin/wrangler secret put ANTHROPIC_API_KEY --config wrangler.toml --env production
# paste the key from the Anthropic console
```

**Then verify.** Call `POST /api/fix/propose` with `{ "provider": "claude" }` in
the body and confirm the response's `provider` is `claude` and `model` is a
`claude-*` id (`providers.js:187` propagates `body.model`). A
`provider_not_configured` error means the secret did not take.

**Rollback.** `wrangler secret delete ANTHROPIC_API_KEY` — provider selection
falls back to kimi.

## Task A3 — (Optional) set `OPENAI_API_KEY`

**Why this matters:** enables the OpenAI leg of `llmChat` (`llm.js:178`) and the
`openai` fix provider. Purely additive; nothing depends on it. `OPENAI_API_KEY`
*is* already listed in the required-secrets block (`wrangler.toml:487`) unlike
the two above, so it may already be set — verify before adding.

```bash
cd worker
./node_modules/.bin/wrangler secret list --config wrangler.toml --env production   # is it already there?
./node_modules/.bin/wrangler secret put OPENAI_API_KEY --config wrangler.toml --env production
```

**Then verify.** `POST /api/fix/propose` with `{ "provider": "openai" }`;
confirm `provider: "openai"` in the response.

**Rollback.** `wrangler secret delete OPENAI_API_KEY`.

## Task A4 — Confirm the AI Gateway's spend/budget feature set

**Why this matters:** the metering plan
([AI-USAGE-METERING-PLAN.md](./AI-USAGE-METERING-PLAN.md)) proposes splitting
work between an Algosize-owned `ai_usage` table and Cloudflare-native gateway
controls (rate limits, spend caps, per-request metadata). Whether the gateway
supports per-user budgets and which metadata dimensions it accepts is a
**control-plane fact that could not be verified from the checkout**, and it is
the load-bearing assumption for the split.

**This is dashboard/manual, not a command.** In the Cloudflare dashboard, open
the `algosize-ai` gateway (from Task A1) and confirm, against current Cloudflare
docs:

- does it expose **rate limiting** per gateway? per metadata key?
- does it support **spend / budget limits**, and at what granularity?
- which **custom metadata** dimensions can be attached to a request, and are
  they queryable in analytics? (The plan wants `org`, `user`, `repo`, `feature`,
  `scan_id`, `fix_task_id`.)

**Verification / output.** Record the answers in
[AI-USAGE-METERING-PLAN.md](./AI-USAGE-METERING-PLAN.md) under "Cloudflare-native
half — confirmed capabilities." Until then that half of the plan stays marked
`unclear`, and the Algosize-owned `ai_usage` table (Task A-repo, below) is the
authoritative meter.
