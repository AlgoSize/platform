Scoring

The 9.8 is computed, not copied.

OSV publishes severity as a vector string. The text rating printed beside it is a convenience field, and it is frequently absent, stale, or disagrees with the vector. We score the vector.

Base metrics, parsed

  • AV:N Attack vector Network · 0.85
  • AC:L Attack complexity Low · 0.77
  • PR:N Privileges required None · 0.85
  • UI:N User interaction None · 0.85
  • S:U Scope Unchanged
  • C:H I:H A:H Impact High · 0.56 each

Base score, derived

Exploitability
8.22 × 0.85 × 0.77 × 0.85 × 0.85 = 3.89
Impact sub-score
1 − (1 − 0.56)³ = 0.9148
Impact
6.42 × 0.9148 = 5.87
Base
roundup(5.87 + 3.89) = 9.8

Rounding is CVSS v3.1 “Roundup”, done in integer arithmetic — the floating-point shortcut scores a handful of real vectors one tenth low.

  • CVSS v3.1 and v3.0 base scores are computed from the published vector — per the FIRST specification, not read off a text rating. v2 vectors are scored with the v2 equations.
  • CVSS v4.0 vectors are approximated, and say so — the v4 base score needs a lookup table we do not ship yet, so those advisories carry an explicit “approximate” flag rather than a confident wrong number.
  • An advisory with no usable severity data is reported as unknown — never silently downgraded to “low” to keep a dashboard green. Unknowns cap the run at a C.
  • A truncated scan is labelled a floor, not a total — if a run hits an internal cap, the report says the counts are a lower bound instead of presenting a partial answer as a clean bill of health.
Where it runs

On the pull request, on a schedule, and in your inbox.

One audit engine, three places it reaches you. The same bytes produce the same answer in all three — the CI path and the dashboard path call the same function.

Gate the pull request

A workflow file collects your lockfiles and posts them. The report comes back as SARIF 2.1.0 for the Security tab, as one sticky PR comment that updates in place, and as an exit code. Set fail_on to the severity you actually block on.

SARIF 2.1.0 security-tab format

Re-scan on a schedule

Advisories get published against code that has not changed. Point a monitor at a repo and branch, and it re-scans nightly or weekly. The alert email carries only what is new since the previous run, so a quiet week produces no mail at all.

diff only new findings only

Catch the committed secret

Live credentials and private key material in source, with the file and line. The remediation says rotate first and purge history second, because deleting the line does not undo the exposure — and one exposed credential caps the run at an F regardless of what else is clean.

rotate → purge in that order
